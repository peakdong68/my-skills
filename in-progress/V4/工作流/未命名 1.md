# Engineering Workflow

Route engineering work through:

    Discuss → Plan → Implementation Gate → Implement → Verify

Use the corresponding skill for each stage.

This document defines cross-stage orchestration, gates, authorization, and return paths. Stage-specific methods belong to their skills.

Planning approval and execution authorization are separate gates.

A plan may establish that work is ready to implement, but code must not be modified until execution is authorized under repository rules.

Use the project's existing artifact types, statuses, labels, approvals, or other workflow conventions to represent these transitions. Do not require a particular status name.

## Discuss

Resolve enough ambiguity to determine whether the work can be implemented directly or requires planning.

Do not formalize exploratory conversation into planning artifacts unless the work is actually proceeding into Plan.

## Plan

Enter `plan` when implementation would otherwise require inventing a material product, scope, domain, architectural, interface, compatibility, or other contract decision.

Skip Plan when the work is already sufficiently defined.

Plan owns planning performed through this workflow and uses Plan Review as its exit gate.

Plan Review establishes whether the authoritative planning set is ready to pass the Implementation Gate. Record that result using the project's workflow convention.

If a later stage exposes a material unresolved contract decision, return to Plan and re-establish planning approval before continuing.

## Implementation Gate

Implementation may begin only when both conditions hold:

1. **Readiness** — the authoritative work is sufficiently defined, required decisions and blockers are resolved, and the project's workflow considers it executable.
2. **Authorization** — code execution has been explicitly requested or otherwise authorized under repository rules.

The authoritative work may be represented by a Proposal, Spec, issue, ticket, accepted plan, or another project-defined artifact.

Do not create a Proposal, Spec, status, or approval solely to satisfy this workflow when the project already has an authoritative readiness mechanism.

## Implement

Enter `implement` only after the Implementation Gate passes.

Use the project's workflow convention to record that execution has begun when such tracking exists.

### Decomposition

Implement directly when the work fits one coherent execution unit.

Use implementation tickets when the work has meaningful independent slices, dependencies, or is too large to execute coherently as one unit.

When tickets are used:

- follow their dependency frontier rather than arbitrary ordering
- execute independent frontier work in parallel when safe and supported
- keep each completed ticket coherent and verifiable
- update visible work tracking as execution progresses
- complete and close each ticket according to the configured tracker workflow
- commit completed ticket work when repository workflow expects ticket-level commits

Do not create tickets merely to enumerate coding steps.

### Execution

Implement against the agreed contract and accepted design.

Test appropriately while working and review the resulting change before handing it to verification.

Do not stop at the first working implementation when authorized end-to-end work still has remaining implementation, review, or verification steps.

### Findings

Route discovered issues by ownership:

| Finding | Route |
|---|---|
| Current implementation is missing or violates the agreed contract | Fix in the current implementation |
| Additional execution unit is needed within the same agreed work | Add or update an implementation ticket |
| Product or technical contract must change or was never resolved | Return to `plan` |
| Issue is unrelated to the agreed work | Do not expand scope automatically |

There is no "fix it while we're here" path for unrelated work.

When implementation, relevant checks, and material review findings are complete, record that the work is ready for final verification using the project's workflow convention.

## Verify

Enter `verify` from completed and reviewed implementation.

Use the project's workflow convention to record verification progress when such tracking exists.

Verify the agreed work using the strongest practical evidence.

If verification fails, route the failure to its owner:

- implementation defect → `implement`
- verification defect → fix verification and retry
- contract ambiguity → `plan`
- environment or tooling failure → resolve or report the blocker
- unrelated pre-existing failure → do not expand scope automatically

After an in-scope fix, verify again.

Only successful verification marks the work complete under the project's workflow convention.

## Return rule

Return to the earliest stage that owns the unresolved issue.

Do not compensate for an upstream contract gap in implementation.

Do not compensate for an implementation defect by weakening verification.
