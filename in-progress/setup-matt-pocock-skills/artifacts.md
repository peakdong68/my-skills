## 生效范围

本约定管理工程工件的查找、创建、更新和生命周期，不要求生成全部工件。日常文档治理直接处理并检查；实质改变工程合同的修改按工程流程处理。

多上下文只分布领域资料：根目录 `CONTEXT-MAP.md` 可指向各项目的 `CONTEXT.md`，本注册表可登记各上下文的 ADR、Spec 等工件位置。新建 Agent Notes 统一部署在根目录 `.agents/notes/`，子项目不另建注册表或记录系统。既有分散位置保留其登记归属，合并迁移需单独授权。

## 新工件归属

| 工件或信息 | 位置与规则 |
| --- | --- |
| Proposal / 总体及阶段提案 | 按 `docs/agents/issue-tracker.md` 已配置的位置、标识及工作状态管理；作为该规划工作的主入口，引用独立需求与设计；未配置时先提示用户配置 |
| Agent Notes / 工程变更与决策记录 | 采用记录系统时，未交付记录在 `.agents/notes/proposed/<分类>/日期-主题.md`，已交付并验证的记录在 `implemented/` 对应分类；保存重要决定与交付理由，可引用 Proposal，不复制提案正文 |
| 独立技术设计 RFC | `docs/rfcs/`；需要独立评审、复用或演进时拆出，由提案引用 |
| 独立行为合同 Spec | `docs/specs/`；明确需要时创建，优先更新同一工作已有 Spec |
| 持久决定 / ADR | 优先由变更记录承载；需要独立 ADR 时在此登记具体位置及职责边界 |
| 既有工作项 / 阶段进度 | 按 `docs/agents/issue-tracker.md` 配置；既有工作项能明确本次范围、验收及决定时可直接复用，不另建 Proposal |
| 实施 Ticket | 按跟踪器配置存储与跟踪，关联所属工作项 |
| PRD 或其他已有工件 | 登记项目已有位置；本方法不要求另建 PRD，未配置时由现有权威产品工件拥有需求 |

文件有真实内容时才创建。变更记录分类读取 `.agents/notes/config.json`；项目规范和同类在维护工件优先作为格式依据。实际命名及格式参考在相应位置规则中补充。

上下文划分与记录分类分别管理，不自动一项目一分类。同一决定只保留一个权威属主；已由上下文 ADR 承载时，Agent Notes 引用它，不复制决定正文。仓库级和上下文级决定的适用范围及具体位置在上表登记。

## 生命周期与批准

变更记录遵循 `.agents/notes/README.md`：proposed 表示尚未或部分交付，implemented 表示所记范围已交付并验证，rejected 表示否决。批准依据和执行授权分别遵循项目约定。

Proposal 的工作状态由跟踪器配置拥有；Plan Review 结果写回本次 Proposal 或既有工作项，取得所需批准后才能更新准备实施状态。记录目录及状态不替代评审、批准或执行授权。历史上同一文件兼任提案和记录的，明确登记其工作状态、批准与交付生命周期映射，不新增竞争状态字段。

独立 RFC、Spec、ADR 不随变更记录移动。在此登记它们已有的审阅、批准和替代约定；未规定时不从文件生成推断批准。Issue/Ticket 状态由跟踪器配置管理。

总体提案链接阶段工作项，各工程单元按需运行工程循环。阶段完成还需集成与阶段验收；覆盖总体范围的变更记录在全部交付前保持 proposed，提案进度按跟踪器约定维护。

## 维护

重新 setup 默认检查和补齐配置，已有差异保留并报告。明确选择新位置时更新本注册表与项目指令；只有授权迁移时才移动历史工件、转换状态并修复链接。注册不新增执行权限。
