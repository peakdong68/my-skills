# 文档标准

本文件是目标仓库文档的统一入口。下面的相对链接以部署位置 `docs/AGENTS.md` 为基准；若项目使用其他入口，应调整链接。部署前结合目标仓库的文档类型和已有属主调整位置表；保留项目中不冲突的规则，并让每项规则只在一个权威位置维护。

## 文档分层

下表列出常见文档及典型职责，供项目识别已有内容归属；它不是必须齐备的模板。项目可以按实际需要合并文档、采用其他名称或增加专门文档，也可以不采用某一类型。

| 常见文档 | 通常负责什么 | 不重复承载什么 |
| --- | --- | --- |
| README / 项目指南 | 项目入口、常见使用方式与进一步阅读路径 | 已由 Spec 或设计文档完整拥有的合同 |
| PRD / 产品说明 | 用户问题、目标、价值和产品边界 | 详细技术实现方案 |
| Proposal / Ticket / 工作项 | 本次交付范围、状态、评审/批准事实和工件链接 | 仓库内的产品合同或设计正文 |
| Spec / 行为规范 | 已确定的行为合同、约束与可观察验收条件 | 讨论过程和技术方案全文 |
| RFC / 设计文档 | 技术方案、关键约束、取舍、迁移及验证影响 | 产品范围和交付进度 |
| ADR / 架构决策记录 | 需要长期保留的架构选择与真实权衡理由 | 完整合同、实现状态和工单进度 |
| Domain / Architecture 文档 | 领域术语、边界、模块职责和关系 | 临时工作状态与实施步骤 |
| Agent Note | 本次变更独有的决定理由、后果和验证 | 其他文档已拥有的合同或决定正文 |
| AGENTS.md / 技能 | Agent 行为规则、工作方法和仓库护栏 | 产品及运行时合同 |

按项目已有属主填写适用位置；不存在的位置不要为了满足表格而新建。研究、验证清单、平台事实和外部参考等专门资料按需建立，不构成默认文档层。既有内容继续由原属主维护，迁移前需获得相应授权。其他位置链接到事实的属主，不复制事实。

## 一个事实一个家

每个事实由负责它的文档层完整说明，其他位置只链接。行为合同归 Spec，技术方案归 RFC，难以逆转的架构决定及其权衡归 ADR，一次变更独有的交付理由与验证归 Agent Note。Proposal/Ticket 管工作范围与进度，不复制仓库合同、设计或决定正文。

- 一份文档的读者和用途决定它写多细；别替其他层写细节，在当前位置链接到内容属主。
- 每种文档只对自己的主题写全；不要把其他主题的清单抄进来。
- 机器能生成或校验的清单（例如迁移列表、路由表、测试清单、包和端点目录）不手抄，链接到源码或生成物。
- 写文档先确定归属和位置，再确定本层的细节程度；不属于本层的内容搬回属主，原地留下链接。
- 文档类型不扩大它的职责。Spec 修订记录只保留修订标识、受影响章节、合同变化摘要和生效情况；不记录讨论过程、理由或被否方案。

## 写作规则

- **写当前状态**：变更过程归提交与 Agent Note；Spec 可以保留只说明合同变化的修订记录。正文写仍生效的内容，不写迁移叙述或代码在调用栈中的位置。
- **保留完整命题**：删形容词、重复和叙述前，确认事实仍完整，包括执行者、动作、条件、时序、义务强度、负向保证、例外、归属、副作用、失败方式与后果。
- **注释和 doc comment 写完整合同，不写推理记录**：保留行为、失败、时机、所有权、义务、例外、后果和不显然的使用方式；删旁白、测试走演、评审分析和代码重述。本地合同写在使用处；理由链接到 ADR、设计或 Agent Note。相邻函数不要重复同一段理由，把它放到拥有该能力的模块或辅助函数。
- **一个段落一行**：用编辑器软换行；表格、代码块和列表保持原有格式。
- **事实与推论分开**：可核实的事实标明证据位置，例如用例名、命令、留档路径或上游文档；推论、估计与待确认事项明确标注，不写成既成事实。
- **合同与记录在仓库内闭环**：使用者在仓库内能读到完整合同，包括行为、失败、限制和使用方式。为什么这样决定，只链接到拥有理由的仓库文档。新增或实质改写的文档使用相对链接；既有历史引用不要求专项清洗。工作跟踪器拥有工作状态，不代替仓库合同、设计或决定。
- **用能指向具体对象的词**：写端点、字段、类型、表、命令或行为本身。对“面”“形状”“契约”等宽泛词先检查是否有更准确的名称；只有表达调用方、实现方、生产者或消费者真正依赖的前置条件、后置条件、不变量或兼容承诺时才用“契约”。复用仓库已定义的术语。
- **不写推理过程**：保留结论、合同和未来仍有用的理由；删除实现步骤叙述、显然分支推导、测试走演、评审过程与被否决的局部备选。
- **不写状态标注**：避免“已实现”“未来会……”等会随交付腐坏的文字；由工作跟踪器、目录和代码表达状态。
- **强调节制**：加粗只用于改变行为的句子或真正重要的对比；不要处处标重点。
- **统一语言与术语**：遵循仓库选定的语言和术语表；同一概念使用同一名称。
- **一节只讲一件事**：一段包含多条规则和括号补充时，拆开内容或将细节移到其属主。

## 按位置补什么

按位置补充缺失信息；已有内容完整时不为套模板而增加文字。

| 位置 | 写清什么 |
| --- | --- |
| 模块说明与公开 API 文档注释 | 模块职责、依赖和非显然架构选择（理由链接到 ADR 或设计）；公开函数的行为差异、错误与失败、副作用、所有权、时机、取消和持久化语义 |
| 其他代码注释 | 不变量、并发与顺序、所有权、安全边界，以及会让调用者意外的失败行为；只写不显然的事实 |
| 测试 | 只解释不显然的测试设计，例如 fixture、断言或平台分支的原因；删掉步骤走查与用例清单 |
| README 与 `docs/` 正文 | 消费者要遵守的合同：配置、语义、失败、限制与扩展点 |
| Agent Note | 本次变更独有的理由、真实备选、后果和验证；格式与生命周期见部署后的 [Agent Notes README](../.agents/notes/README.md) |
| 技能与 Agent 指令 | 行为护栏和明确范围限制；保持简短，链接到规则属主 |
| 用户可见字符串、日志与诊断 | 文字本身属于行为，修改时运行拥有该输出的用例；诊断点名失败主体或路径、违反的规则和修复方式 |

## Slop 清单

审阅时检查并删改这些内容：

- 同一规则出现在多处：搜索特征短语，保留一个属主，其他位置改成链接。
- 历史写进当前规则层；实现状态写进正文或图中，例如“已实现”“未来”。
- 手抄源码或生成器已经拥有的目录、API、迁移、路由或测试清单。
- 推理过程、显然分支的证明、测试走演、评审记录和被否决的局部备选。
- 注释复述代码已经表达的控制流、字段名或类型。
- 同一理由重复放在相邻的兄弟函数旁，而不是写在拥有理由的模块或能力上。
- 一段塞进多条规则、多个主题或过多括号补充。
- 加粗、全大写或“关键的是”膨胀到处都是。
- implemented Agent Note 使用规格语气、迁移计划或验收清单；交付记录应陈述事实。
- 新增或实质改写的仓库文档把范围、验收、设计、决定、批准或交付记录交给 Issue/PR，而非仓库里的相应属主。

## 怎么审

先界定审查范围，再读取本文件和每类内容的属主。逐项判断保留、补写、删减或移走；“移走”表示将事实放回真正拥有它的文档。先改事实属主，再更新派生引用。交付审查结果时说明覆盖范围、实际修改、刻意保留的内容和未确定事项；证据不足时保留原文并报告不确定性，不猜测补齐。

## 检查

Agent Note 的目录、元数据、正文骨架和本地链接由部署后的 `node scripts/decisions/check.mjs` 检查，细则见 [Agent Notes README](../.agents/notes/README.md)。运行该项目已配置的文档和代码检查；不要把某一语言或仓库专属命令复制成所有项目的要求。机械检查通过不代替对事实归属、内容真实性与合同完整性的审阅。
