# 文档标准

本文件是目标仓库文档的统一入口。下面的相对链接以部署位置 `docs/AGENTS.md` 为基准；若项目使用其他入口，应调整链接。部署前结合目标仓库的文档类型和已有属主调整位置表；保留项目中不冲突的规则，并让每项规则只在一个权威位置维护。

## 文档分层

下表列出常见文档及典型职责，供配置时识别内容归属；它不是必须齐备的模板。本项目各类工件的属主、位置与适用范围以部署时填写的归属配置为准。项目可以按实际需要合并文档、采用其他名称或增加专门文档，也可以不采用某一类型。

| 常见文档 | 通常负责什么 | 不重复承载什么 |
| --- | --- | --- |
| README / 项目指南 | 项目入口、常见使用方式与进一步阅读路径 | 已由 Spec 或设计文档完整拥有的合同 |
| PRD / 产品说明 | 用户问题、目标、价值和产品边界 | 详细技术实现方案 |
| Proposal / Ticket / 工作项 | 本次交付范围、产品行为与验收、状态、评审/批准事实和设计链接 | 长期技术决定的正文 |
| Spec / 行为规范（按需） | 跨工作项持续生效的行为合同、约束与可观察验收条件 | 讨论过程和技术方案全文 |
| RFC / 设计文档（按项目配置） | 登记范围内的技术设计资料 | 工作状态和重复的 Agent Note |
| ADR / 架构决策记录（按项目配置） | 登记范围内的架构决定资料 | 重复的 Agent Note |
| Domain / Architecture 文档 | 领域术语、边界、模块职责和关系 | 临时工作状态与实施步骤 |
| Agent Note | 面向后续维护代码的 Agent 与人类维护者，保存长期有价值的技术提案与决定、真实备选、理由及后果 | 产品合同、工作状态和已有权威设计全文 |
| AGENTS.md / 技能 | Agent 行为规则、工作方法和仓库护栏 | 产品及运行时合同 |

按项目配置填写适用位置；不存在的位置不要为了满足表格而新建。研究、验证清单、平台事实和外部参考等专门资料按需建立，不构成默认文档层。阅读和写入都遵循配置指定的属主与适用范围；归属缺失或冲突时报告受影响内容与配置缺口。其他位置链接到事实的属主，不复制事实。

## 项目归属配置

下面是新项目采用 Planning／Agent Notes 时的配置示例。部署时替换工作项占位项和示例路径，按项目已选属主与范围填写；已有项目复用其登记，归属切换按 setup 的登记流程处理。仅填写本次配置涉及的类型，其他已配置类型保留原规则。常见文档职责表用于识别类型，本节填写实际读取与写入路线。

```markdown
| 内容或类型 | 启用方式与适用范围 | 属主、位置与规则入口 |
| --- | --- | --- |
| Proposal／Issue | 已启用；本次交付范围、产品行为与验收 | 项目选定的工作项；填写实际跟踪器、仓库或本地创建路径，并链接其配置 |
| 工作状态、评审与批准证据 | 已启用；工作项推进 | 已配置的工作跟踪器；链接其状态与证据规则 |
| Agent Note | 已启用；长期技术提案、设计、决定、备选与理由 | `.agents/notes/`（相对仓库管理根目录）；格式与生命周期见其 README，记录范围与路径按其 config 和 README；工作项链接到 Note |
| 独立 RFC／ADR | 新工作未启用 | 相应技术设计与决定归 Agent Note |
| 独立 Spec | 按需启用；跨工作项持续生效的行为合同 | 首次需要时先登记合同属主、适用范围、位置与规则，再创建正文 |
```

已启用类型即使还没有记录，也应登记位置或创建规则及可到达的规则入口；Agent Notes 同时明确已选记录范围。记录目录在首份记录需要时创建，管理规则与工具按所选配置部署。未启用类型说明其内容归哪里，按需类型说明首次启用前的登记要求。检查时按配置判断归属；目录是否存在不代表类型是否启用。

## 一个事实一个家

每个事实由负责它的属主完整说明，其他位置只链接。本次产品行为与验收归工作项；跨工作项持续生效的合同可按需由独立 Spec 或已有规范拥有。Planning 中需要长期保留的新技术设计与决定归 Agent Note，包括真实备选和理由，工作项从自身链接到 Note。其他适用输入按项目归属配置读取。工作跟踪器拥有状态、评审和批准证据。

- 一份文档的读者和用途决定它写多细；别替其他层写细节，在当前位置链接到内容属主。
- 每种文档只对自己的主题写全；不要把其他主题的清单抄进来。
- 机器能生成或校验的清单（例如迁移列表、路由表、测试清单、包和端点目录）不手抄，链接到源码或生成物。
- 写文档先确定归属和位置，再确定本层的细节程度；不属于本层的内容搬回属主，原地留下链接。
- 文档类型不扩大它的职责。Spec 修订记录只保留修订标识、受影响章节、合同变化摘要和生效情况；不记录讨论过程、理由或被否方案。

## 写作规则

- **写当前状态**：变更过程归提交与工作项；Agent Note 保存仍有长期价值的决策依据，implemented Note 写实际交付的决定并同步事实。独立 Spec 可以保留只说明合同变化的修订记录。
- **保留完整命题**：删形容词、重复和叙述前，确认事实仍完整，包括执行者、动作、条件、时序、义务强度、负向保证、例外、归属、副作用、失败方式与后果。
- **注释只补充代码无法表达、读者必须知道的行为与约束**：公开 API 的 doc comment 写清调用方依赖的合同；内部注释只写必要的非显然信息，不复述代码、不记录推理过程。长期设计理由可链接适用的已交付 Agent Note；不链接 ADR、RFC／设计文档、Proposal、Ticket 或 Issue。
- **一个段落一行**：用编辑器软换行；表格、代码块和列表保持原有格式。
- **事实与推论分开**：可核实的事实标明证据位置，例如用例名、命令、留档路径或上游文档；推论、估计与待确认事项明确标注，不写成既成事实。
- **合同与记录能追溯到属主**：本次范围与产品验收可由工作项拥有；跨工作项持续生效的合同按需在仓库文档中维护。代码和现有文档无法解释的长期设计理由由 Agent Note 拥有。新增或实质改写的仓库文档使用相对链接；既有历史引用不要求专项清洗。
- **用能指向具体对象的词**：写端点、字段、类型、表、命令或行为本身。对“面”“形状”“契约”等宽泛词先检查是否有更准确的名称；只有表达调用方、实现方、生产者或消费者真正依赖的前置条件、后置条件、不变量或兼容承诺时才用“契约”。复用仓库已定义的术语。
- **不写推理过程**：保留结论、合同和未来仍有用的理由；删除实现步骤叙述、显然分支推导、测试走演、评审过程与被否决的局部备选。
- **不写状态标注**：避免“已实现”“未来会……”等会随交付腐坏的文字；由工作跟踪器、目录和代码表达状态。
- **强调节制**：加粗只用于改变行为的句子或真正重要的对比；不要处处标重点。
- **统一语言与术语**：遵循仓库选定的语言和术语表；同一概念使用同一名称。
- **一节只讲一件事**：一段包含多条规则和括号补充时，拆开内容或将细节移到其属主。

## 按位置补什么

按位置补充缺失信息；已有内容完整时不为套模板而增加文字。

| 位置 | 写清什么 |
| --- | --- |
| 模块说明与公开 API 文档注释 | 模块职责、依赖和非显然架构选择；公开函数的行为差异、错误与失败、副作用、所有权、时机、取消和持久化语义。长期设计依据的引用遵循上面的注释规则 |
| 其他代码注释 | 不变量、并发与顺序、所有权、安全边界，以及会让调用者意外的失败行为；只写不显然的事实 |
| 测试 | 只解释不显然的测试设计，例如 fixture、断言或平台分支的原因；删掉步骤走查与用例清单 |
| README 与 `docs/` 正文 | 消费者要遵守的合同：配置、语义、失败、限制与扩展点 |
| Agent Note | 长期技术提案、已交付决定、真实备选和后果；格式与生命周期见部署后的 [Agent Notes README](../.agents/notes/README.md) |
| 技能与 Agent 指令 | 行为护栏和明确范围限制；保持简短，链接到规则属主 |
| 用户可见字符串、日志与诊断 | 文字本身属于行为，修改时运行拥有该输出的用例；诊断点名失败主体或路径、违反的规则和修复方式 |

## Slop 清单

审阅时检查并删改这些内容：

- 同一规则出现在多处：搜索特征短语，保留一个属主，其他位置改成链接。
- 历史写进当前规则层；实现状态写进正文或图中，例如“已实现”“未来”。
- 手抄源码或生成器已经拥有的目录、API、迁移、路由或测试清单。
- 推理过程、显然分支的证明、测试走演、评审记录和被否决的局部备选。
- 注释复述代码已经表达的控制流、字段名或类型。
- 同一理由重复放在相邻的兄弟函数旁，而不是写在拥有理由的模块或能力上。
- 一段塞进多条规则、多个主题或过多括号补充。
- 加粗、全大写或“关键的是”膨胀到处都是。
- implemented Agent Note 使用规格语气、迁移计划或验收清单；交付记录应陈述事实。
- 新增或实质改写的仓库文档把长期设计或决定只留在 Issue/PR 评论中，而没有同步到已经选定的 Agent Note 属主。

## 怎么审

先界定审查范围，再读取本文件和每类内容的属主。逐项判断保留、补写、删减或移走；“移走”表示将事实放回真正拥有它的文档。先改事实属主，再更新派生引用。交付审查结果时说明覆盖范围、实际修改、刻意保留的内容和未确定事项；证据不足时保留原文并报告不确定性，不猜测补齐。

## 检查

Agent Note 的目录、元数据、正文骨架和本地链接由部署后的 `node scripts/decisions/check.mjs` 检查，细则见 [Agent Notes README](../.agents/notes/README.md)。运行该项目已配置的文档和代码检查；不要把某一语言或仓库专属命令复制成所有项目的要求。机械检查通过不代替对事实归属、内容真实性与合同完整性的审阅。
