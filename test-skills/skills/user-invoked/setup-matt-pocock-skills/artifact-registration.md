# Establish document ownership

During setup, locate the repository management root from project instructions and existing owners; use Git top-level only when no project boundary is established. Working in a subproject does not silently create another management root. Resolve recorded paths from that root, while Markdown links remain relative to their files.

Inspect current project instructions, document conventions, representative artifacts and work tracking. Record the agreed document types, owners, new locations and historical exceptions in the project's existing document entry, normally `docs/AGENTS.md`. Use [docs-agents.md](docs-agents.md) as a starting point when no owner exists. If a project already uses one as an owner, preserve that routing until an authorized consolidation is complete.

For each artifact, identify its authoritative owner: the tracker owns work status, review and approval evidence; the work item owns its delivery scope, product behavior and acceptance; an independent Spec may own a behavior contract that stays effective across work items. When configuring the Planning workflow, register Agent Notes for new durable technical proposals, designs, decisions, alternatives and rationale. A root `GLOSSARY-MAP.md` can direct readers to context-local documents; the Notes root config separately selects record directories. Contexts do not create record categories.

Setup establishes which existing Specs, RFCs, ADRs and other records remain applicable, which are historical, and where new work belongs. Inspect actual references and required contracts or decisions; file existence or an old status alone is insufficient. Write the agreed owners, paths, applicable scopes and historical identities into the project document entry. Consumer skills read that configuration rather than deciding historical ownership themselves.

For existing files that combine a work item and a design record, register their responsibilities and state mapping separately. Configuration changes do not automatically split files or add competing status fields.

For an authorized ownership change, first present the old-to-new owner mapping, affected scopes, unresolved decisions and the order of the switch. Establish the new owner's complete content and required review before removing the old owner's authority, then update scope/status labels and active references. If a still-needed contract or decision lacks a settled owner, record the gap and its impact on dependent work. Preserve files and customizations outside the authorized change; installing Notes alone does not authorize archiving, moving, deleting or rewriting existing artifacts.

For each document type needed by the selected workflow, register its owner, applicable scope, concrete destination or creation rule, and pointer to its format/lifecycle rules during setup, even when it has no records yet. For Agent Notes, record the management-root-relative Notes location and point to its README and config for record paths and selected scopes. Register the location before the first record; create record directories when that record needs them. Deploying management rules and tools follows [decision-records.md](decision-records.md).

In a new Planning/Agent Notes configuration, explicitly mark standalone RFC/ADR as not enabled for new work and route their design and decision content to Notes. Record independent Spec as on demand when no cross-work-item behavior contract needs one yet; its activation requires registering an owner and location before writing the contract. Existing configured owners and explicitly selected independent ADR use their registered scope and destination. Directory absence does not establish whether a type is enabled or where its content belongs. Do not register `docs/specs/`, `docs/design/` or `docs/adr/` by default or create empty artifacts. Reuse sufficient settled configuration; configuring a subset of skills does not require deploying the entire workflow.

Verify that root and subproject readers reach the same document ownership entry, every active artifact has one owner, historical paths remain discoverable, and tracker approval and delivery status are distinct. For each selected workflow, verify that a first work item or decision can be routed from the configuration: enabled types have a destination or creation rule and reachable governing rules; disabled types name their content owner; on-demand types define registration before first use. Report unresolved required routing as a setup gap. Refer to the tracker and Notes rules from the document entry instead of repeating their mechanics there.
