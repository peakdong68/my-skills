# 区分工程闭环与独立验收的证据和汇报

## 决定与依据

本次工作项为本任务会话中用户对两份技能的改进请求，范围与验收依据为双方已确认的逐项证据、修正边界及最终汇报约定；无独立会话链接。此记录保存职责决定与交付依据，不引入额外提案或跟踪状态。

[verify](../../../../skills/model-invoked/verify/SKILL.md) 是工程工作流最后一环，在已有范围与授权内归因、修正、按所属阶段完成必要审查后重验；首次失败不终止工作。汇报最新验收状态，已修复且重验通过的失败归入修正摘要。只有全部必需条件通过才能完成工程。

[to-verify](../../../../skills/user-invoked/to-verify/SKILL.md) 是用户手动发起的独立只读验收，报告交付物当前状态、证据及所需修正，由用户另行请求修复。诊断不修改交付物，不自动发布外部评论或推进工程完成状态。

两者均以批准合同而非实现推导预期，逐项关联证据与 PASS、FAIL、BLOCKED；发现失败后继续检查独立条件，按风险检查相关回归。既有问题影响验收时保留其影响及归属，不能凭“没有发现问题”宣告通过。

借鉴 review-agent 的具体证据、完整覆盖和可行动问题表述，不搬入其仅限新增缺陷、diff 行号或 No findings 的审查判定。保留两份技能独立使用的能力，不新增互相调用或共享路由。代价是少量共同验收规则分别维护，职责差异在各自文件中直接可见。

## 验收依据

- 必需条件证据不足或合同歧义时不得 PASS；已证实失败但根因未知时仍为 FAIL。
- 首条失败不遗漏独立条件；既有问题影响合同也需报告。
- verify 在范围内修正与重验后汇报最新状态，仅全部通过才推进完成；无法继续时说明所需行动。
- to-verify 保持只读并交付当前报告，不自动修复、发布评论或推进状态。
- 汇报包含合同关联、证据、相关回归及实质验证局限，已修正问题不残留为当前失败。

实现范围为上述两份 SKILL.md 及本仓库记录、索引，不修改调用策略、安装副本或其他工程技能。

## 交付与验证

已交付上述职责、验收覆盖和汇报规则。Standards 审查无实质违规，清除了一个空标题；Spec 审查发现报告顺序与回归结果交付缺口，已修正并复核通过。

逐项核对情境：首次失败后继续独立验证；范围内修正重验通过后汇报 PASS；有失败且有阻塞时总体 FAIL；无失败但缺少必需证据时 BLOCKED；根因未知不覆盖已证实 FAIL；既有问题不被遗漏或自动扩大修复范围；独立验收不发起修复或推进状态。上述为文义审阅，不是代理运行时行为测试。

verify 通过 quick_validate.py。to-verify 保留原始手动调用元数据：原校验器不接受既有 disable-model-invocation 扩展字段，已单独核对其值及整个 frontmatter 与基线一致，并仅在临时副本中移除该字段检查剩余格式，通过后临时副本自动清理。两份技能本地链接检查通过，使用 UTF-8 模式运行校验以避免 Windows 默认编码误读。

记录索引由 node scripts/decisions/update-index.mjs 生成，并运行 node scripts/decisions/check.mjs 与 git diff --check；保留审批真实性和实际行为效果仍需人工及实际使用验证的边界。
