# 工程工作流

通过以下路径路由工程工作：

    讨论 → 计划 → 实施门禁 → 实施 → 验证

每个阶段使用相应的技能。

本文档定义了跨阶段编排、门禁、授权和返回路径。特定于阶段的方法属于其各自的技能。

计划批准和执行授权是独立的门禁。

计划可能确定工作已准备好实施，但在根据仓库规则授权执行之前，不得修改代码。

使用项目现有的工件类型、状态、标签、审批或其他工作流约定来表示这些转换。不要要求特定的状态名称。

## 讨论

消除足够的歧义，以确定工作是否可以直接实施或需要计划。

除非工作实际进入“计划”阶段，否则不要将探索性对话形式化为计划工件。

## 计划

当实施否则需要发明重大的产品、范围、领域、架构、接口、兼容性或其他契约决策时，进入 `plan`（计划）。

当工作已经定义充分时，跳过计划。

计划拥有通过此工作流执行的规划，并使用计划评审作为其出口门禁。

计划评审确定权威计划集是否准备好通过实施门禁。使用项目的工作流约定记录该结果。

如果后续阶段暴露出未解决的重大契约决策，则返回计划并在继续之前重新建立计划批准。

## 实施门禁

仅当满足以下两个条件时，才能开始实施：

1. **就绪性** — 权威工作已充分定义，所需决策和阻碍已解决，且项目工作流认为其可执行。
2. **授权** — 代码执行已明确请求或根据仓库规则以其他方式获得授权。

权威工作可以由提案、规范、问题、工单、已接受的计划或另一个项目定义的工件表示。

当项目已经存在权威的就绪机制时，不要仅仅为了满足此工作流而创建提案、规范、状态或审批。

## 实施

仅在实施门禁通过后进入 `implement`（实施）。

当存在此类跟踪时，使用项目的工作流约定记录执行已开始。

### 分解

当工作适合一个连贯的执行单元时，直接实施。

当工作具有有意义的独立切片、依赖关系，或者太大而无法作为一个单元连贯执行时，使用实施工单。

当使用工单时：

- 遵循其依赖前沿，而不是任意排序
- 在安全且支持的情况下并行执行独立的前沿工作
- 保持每个完成的工单连贯且可验证
- 随着执行的进展更新可见的工作跟踪
- 根据配置的跟踪器工作流完成并关闭每个工单
- 当仓库工作流期望工单级别的提交时，提交已完成的工单工作

不要仅仅为了枚举编码步骤而创建工单。

### 执行

根据约定的契约和接受的设计进行实施。

在工作过程中适当测试，并在将其交给验证之前评审 resulting 变更。

当授权的端到端工作仍有剩余的实施、评审或验证步骤时，不要在第一个可行的实现处停止。

### 发现

按所有权路由发现的问题：

| 发现 | 路由 |
|---|---|
| 当前实施缺失或违反约定的契约 | 在当前实施中修复 |
| 在同一约定工作中需要额外的执行单元 | 添加或更新实施工单 |
| 产品或技术契约必须更改或从未解决 | 返回 `plan`（计划） |
| 问题与约定工作无关 | 不要自动扩大范围 |

对于不相关的工作，没有“既然在这里就顺便修复”的路径。

当实施、相关检查和重大评审发现完成后，使用项目的工作流约定记录工作已准备好进行最终验证。

## 验证

从已完成并经过评审的实施进入 `verify`（验证）。

当存在此类跟踪时，使用项目的工作流约定记录验证进度。

使用最强的实际证据来验证约定的工作。

如果验证失败，将失败路由给其所有者：

- 实施缺陷 → `implement`（实施）
- 验证缺陷 → 修复验证并重试
- 契约歧义 → `plan`（计划）
- 环境或工具故障 → 解决或报告阻碍
- 不相关的预先存在的故障 → 不要自动扩大范围

在范围内修复后，再次验证。

只有成功的验证才根据项目的工作流约定标记工作完成。

## 返回规则

返回到拥有未解决问题的最早阶段。

不要在实施中补偿上游契约缺口。

不要通过削弱验证来补偿实施缺陷。
