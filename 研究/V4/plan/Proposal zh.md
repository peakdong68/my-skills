# 提案（Proposal）

通过 `plan` 规划的每一项工作都对应一份提案。

提案是该项规划工作的规范根节点。它标识工作内容，并引用权威工件，但不复制其内容。

## 存储

若项目已配置问题跟踪系统（issue tracker），则优先使用它。

否则，将提案本地存储在：

    docs/proposals/<slug>.md

若工作已有提案，则复用该提案。

除非项目明确要求，否则请勿同时创建 Issue 和本地提案。

## 内容

保持提案简洁。

包括：

### 摘要（Summary）

简要描述拟议的变更及其存在的原因。

### 验收标准（Acceptance）

定义认为工作成功所需满足的最低可观察条件。

当另一权威工件（例如 PRD 或 Spec）拥有详细契约时，此处保持简洁。

### 工件（Artifacts）

引用实际存在的权威工件，例如：

- PRD
- Spec
- RFC
- ADR
- 实施工单（implementation tickets）

请勿仅为填充此部分而创建占位工件。

## 状态（Status）

使用项目现有的工作流约定来表示提案状态。

这可能使用：

- 问题跟踪系统的状态
- 标签（labels）
- 审批（approvals）
- 前置元数据（frontmatter）
- 其他已建立的项目机制

当项目已定义状态词汇时，请勿引入并行状态术语。

对于在未建立约定的项目中的本地提案，可使用简单的状态字段：

    ---
    status: planning
    ---

状态应明确体现相关的生命周期区分，例如工作仍处于规划中、已批准实施、被阻塞或已完成。

确切的状态名称属于项目自有约定。

## 更新（Updates）

在以下情况下更新提案：

- 其工作流状态发生实质性变化
- 权威工件被添加、移除、替换或被取代
- 引入了实施工单

当另一工件拥有详细信息时，请勿将详细需求、设计推理、评审发现或实施进度复制到提案中。

## 本地格式（Local format）

    ---
    status: <项目定义的状态>
    ---

    # <标题>

    ## 摘要

    <变更内容及其原因。>

    ## 验收标准

    - <可观察的成功条件>
    - <可观察的成功条件>

    ## 工件

    - PRD: <引用>
    - Spec: <引用>
    - RFC: <引用>
    - ADR: <引用>
    - 工单: <引用>

省略不存在的工件条目。
