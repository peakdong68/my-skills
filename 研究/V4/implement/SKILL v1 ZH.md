# 实施

根据其权威性工作项和引用的契约，实施授权的工作。

假设工程工作流已确立就绪状态和执行权限。

## 分解

当工作适合一个连贯的执行单元时，直接实施。

当工作过大或具有有意义的独立切片或依赖关系时，请阅读 [tickets.md](./tickets.md)。

不要仅仅为了枚举编码步骤而创建工单。

## 执行

根据权威性工作项及其引用的契约、已接受的设计和架构决策进行实施。

除非权威设计明确更改，否则使用既定的架构、约定、接口和领域语言。

根据变更情况编写或更新测试。当测试优先开发能改善反馈或有助于清晰建立行为时，请使用该方法。

在工作过程中运行聚焦测试和相关静态检查。

如果实施暴露出未解决的重大产品、领域、架构、接口、兼容性或其他契约决策，请返回 `plan`（计划），而不是在实施过程中凭空发明决策。

## 实施评审

当实施完成后，沿两个独立的轴对 resulting 变更进行评审：

- **标准** — 对仓库标准、已接受的 RFC 和 ADR、既定架构、约定和约束的忠实度。
- **规范** — 对权威性工作契约的忠实度，包括缺失的行为、错误的行为和非预期的范围。

保持这两个维度相互独立，以便一个维度的通过不会掩盖另一个维度的失败。

按所有权解决重大发现：

| 发现 | 路由 |
|---|---|
| 当前实施缺失或违反商定的契约 | 在当前实施中修复 |
| 在同一商定工作需要额外的执行单元 | 添加或更新实施工单 |
| 产品或技术契约必须更改或从未解决 | 返回 `plan`（计划） |
| 问题与商定工作无关 | 不要自动扩大范围 |

对于无关的工作，没有“顺便修复”的路径。

在最终验证之前解决重大的范围内发现。

## 完成

当满足以下条件时，实施即完成：

- 已实施授权范围
- 所需工单已完成
- 相关实施时检查通过
- 重大实施评审发现已解决
- 变更已准备好进行最终验证

当定义了此类转换时，使用项目的工作流约定更新权威性工作项。
