# 实施

根据权威工作项及其引用的契约来实施已授权的工作。

对于实施工作，假定就绪性和执行权限已由工程工作流确立。

对于仅评审的请求，请使用下面的评审范围和维度，而不进入实施阶段或要求其门禁。交付有证据支持的发现和覆盖范围限制；不要自动修复变更或推进其工作流状态。实施修正和完成规则仅适用于已授权的实施。

## 分解

当工作适合作为一个连贯的执行单元时，直接实施。

当工作规模过大或具有有意义的独立切片或依赖关系时，阅读 [tickets.md](./tickets.md)。

不要仅为了列举编码步骤而创建工单。

## 执行

依据权威工作项及其引用的契约、已接受的设计和架构决策进行实施。

使用既定的架构、约定、接口和领域语言，除非权威设计明确变更了它们。

根据变更适当编写或更新测试。当测试优先开发能改善反馈或有助于清晰建立行为时，使用测试优先开发。

在工作过程中运行有针对性的测试和相关的静态检查。

如果实施暴露出重要的未解决的产品、领域、架构、接口、兼容性或其他契约决策，回到 `plan` 阶段，而不是在实施期间自行决定。

## 实施评审

根据请求和可用上下文建立评审基线和范围。评审完整的范围内变更，包括适用的新增、暂存和未暂存文件；区分既有变更和无关变更。

从两个独立维度评审最终的实施结果，或独立请求的变更范围：

- **标准** —— 对仓库标准、已接受的 RFC 和 ADR、既定架构、约定和约束的忠实度。
- **规格** —— 对权威工作契约的忠实度，包括缺失行为、错误行为和非预期范围。

保持两个维度独立，以便一个维度的通过不会掩盖另一个维度的失败。

在已授权的实施过程中，按所有权解决重要发现：

| 发现 | 路由 |
|---|---|
| 当前实施遗漏或违反了已达成一致的契约 | 在当前实施中修复 |
| 在相同的已达成一致工作内需要额外的执行单元 | 添加或更新实施工单 |
| 产品或技术契约必须变更，或从未被解决 | 回到 `plan` |
| 问题与已达成一致的工作无关 | 不要自动扩展范围 |

对于无关工作，不存在“顺便修复”的路径。

在最终验证之前，解决范围内的重要发现。

## 完成

当满足以下条件时，实施即告完成：

- 授权范围已实施
- 所需工单已完成
- 相关实施阶段检查已通过
- 实施评审中的重要发现已解决
- 变更已准备好进行最终验证

当项目工作流定义了相应状态转换时，使用其约定更新权威工作项。
