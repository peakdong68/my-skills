# 实施工单

仅当授权的工作无法作为一个连贯的单元执行时，才对其进行分解。

工单是执行单元，而非额外的设计文档。

不要利用分解来重新开启上游已确定的决策。

## 存储

使用项目现有的工作跟踪机制。

工单可以是：

- 问题跟踪器中的问题
- 本地 Markdown 文件
- 其他项目定义的执行工件

在项目约定支持的情况下，引用父级或权威性工作项。

## 探针式开发（Tracer Bullets）

优先采用探针式的垂直切片。

每个工单应：

- 交付狭窄但完整的行为或连贯的变更
- 贯穿实现该行为所需的各个层级
- 在可行的情况下独立可验证
- 适合在一个全新的执行上下文中完成
- 使系统保持连贯状态
- 声明真实的阻塞性依赖

优先实现穿过必要层级的单一行为，而非跨越多种行为的单一架构层级。

## 阻塞边

仅声明真正阻止工单开始的依赖项。

没有未解决阻塞项的工单构成可执行前沿。

当工作可以独立进行时，不要创建人为的顺序。

在安全且支持的情况下，独立的前沿工单可以并行执行。

随着工单的完成，重新评估可执行前沿。

## 大规模重构

不要将广泛的机械性变更强制拆分为人为的垂直切片。

必要时，优先采用：

1. **扩展** — 引入新形式并与旧形式并存。
2. **迁移** — 以连贯的批次移动消费者。
3. **收缩** — 在迁移完成后移除旧形式。

显式表示真实的依赖边。

## 工单内容

保持每个工单简洁。

包括：

### 目标

工单交付的行为或连贯变更。

### 验收标准

完成的可观察或可验证条件。

### 阻塞于

仅列出真正的阻塞性工作。

在存在原生依赖机制时使用项目的原生机制。

## 继承

工单从其权威父级工作和引用的工件中继承契约。

这可能包括：

- 提案 (Proposal)
- 产品需求文档 (PRD)
- 规范 (Spec)
- 请求意见稿 (RFC)
- 架构决策记录 (ADRs)
- 项目约束

引用这些来源，而不是复制它们。

避免详细的实施食谱或实施者可以安全自行做出的决策。

## 执行

处理可执行前沿。

在推进依赖工作之前，将每个工单完成至连贯、经过测试且可验证的状态。

根据配置的跟踪器工作流更新并关闭已完成的工单。

当仓库工作流期望工单级别的提交时，提交已完成的工单工作。

继续直到授权范围所需的所有工单都完成。
