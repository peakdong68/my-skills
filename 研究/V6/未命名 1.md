name: planning
description: Use when engineering work still requires material contract or design decisions before implementation can safely proceed.

# Planning

Complete the decisions required to make the selected work implementation-ready.

Planning is synthesis and decision completion, not a fresh interview.

## Authority

Use the project's existing authoritative artifacts and conventions.

These may include:

- Proposal or issue
- PRD
- approved Spec
- RFC
- ADR
- ticket
- another project-defined contract

Do not create a new artifact when an existing authoritative artifact already owns the required information.

## Decisions

Resolve ordinary technical choices directly when they remain within the agreed contract, accepted architecture, and established constraints.

Material unresolved product, business, compatibility, cost, risk, architectural-direction, or other value judgments belong to the user unless that authority has been explicitly delegated.

### RFC

Use an RFC when meaningful technical design must be resolved before implementation.

A draft RFC is not an implementation basis.

It becomes authoritative only when accepted or approved under the project's workflow.

When alternatives materially affect the decision, recommend a preferred direction and preserve enough reasoning for review.

Accepted durable architectural decisions should be preserved as ADRs when warranted.

## Plan Review

Before declaring the work implementation-ready, review the planning set along three independent axes:

- **Standards** — fidelity to accepted ADRs, applicable RFCs, established domain language, and project constraints.
- **Spec** — coverage of the authoritative product or work contract without material omissions, contradictions, or unintended scope.
- **Architecture** — coherence of module boundaries, responsibilities, dependencies, interfaces, and system relationships.

Keep the axes independent so a pass on one does not mask a failure on another.

Review may accept, reject, or require revision of a proposed RFC or design.

Resolve findings in the artifact that owns them.

Questions already governed by accepted contracts, ADRs, RFCs, or project constraints should be resolved from those authorities.

Planning passes only when:

- no material contract or design decision remains unresolved
- required RFCs or equivalent designs are accepted
- material review findings are resolved
- implementation can proceed without inventing material product behavior or architecture

Passing Planning establishes readiness only.

Return control to the engineering workflow for the Implementation Gate.

# Implement

Implement the authorized work against its authoritative contract and accepted design.

Do not expand scope beyond the authorized work.

## Execution

Implement directly when the work fits one coherent execution unit.

Use implementation tickets when the work has meaningful independent slices, dependencies, or is too large to execute coherently as one unit.

When tickets are used:

- follow dependency edges rather than arbitrary ordering
- execute independent frontier work in parallel when safe and supported
- keep each completed execution unit coherent and verifiable
- update the configured work tracker as execution progresses
- complete work items according to the project's tracker conventions

Do not create tickets merely to enumerate coding steps.

Test appropriately while working.

Use test-first development when it materially improves the implementation.

Do not stop at the first working implementation when authorized end-to-end work still has remaining implementation, review, or verification steps.

If implementation exposes a material unresolved contract or design decision, return to Planning rather than inventing it downstream.

## Implementation Review

Before handing completed implementation to final verification, review the resulting change along two independent axes:

- **Standards** — fidelity to repository conventions, accepted ADRs/RFCs, and established technical constraints.
- **Spec** — fidelity to the authoritative work contract, including required behavior, scope, and acceptance criteria.

Keep the axes independent so a pass on one does not mask a failure on another.

### Findings

Route material review findings by ownership:

| Finding | Route |
|---|---|
| Current implementation is missing or violates the agreed contract | Fix in the current implementation |
| Additional execution unit is needed within the same agreed work | Add or update an implementation ticket |
| Product or technical contract must change or was never resolved | Return to Planning |
| Issue is unrelated to the agreed work | Do not expand scope automatically |

There is no "fix it while we're here" path for unrelated work.

Resolve in-scope material findings before proceeding.

When Implementation Review passes, return control to the engineering workflow for PR and final verification.

# Verify

Verify completed and reviewed work against its authoritative contract using the strongest practical evidence available.

Use the project's existing verification commands, checks, CI, and repository conventions rather than inventing a parallel verification process.

When pull requests are used, final verification must include all applicable repository-required checks, CI results, and approvals.

Do not consider the work complete while required verification is pending or failing.

## Failure Routing

If verification fails, route the failure to its owner:

- **implementation defect** → return to Implement
- **verification defect** → fix verification and retry
- **contract ambiguity** → return to Planning
- **environment or tooling failure** → resolve or report the blocker
- **unrelated pre-existing failure** → do not expand scope automatically

After any in-scope fix, verify again.

Do not weaken the contract, tests, or required checks merely to obtain a passing result.

Only successful final verification completes the work.

Return control to the engineering workflow for any required merge or completion transition.
