# Plan

Turn the current conversation and relevant project context into an implementation-ready Proposal.

Planning is synthesis and decision completion, not a fresh interview.

## Proposal

Every planned work item has one Proposal.

Read [proposal.md](./proposal.md) when creating or updating it.

Reuse an existing Proposal when one already represents the work.

## Planning

Create additional artifacts only when needed:

- **PRD** — read [prd.md](./prd.md) when the product contract needs further definition.
- **RFC** — read [rfc.md](./rfc.md) when meaningful technical decisions must be resolved before implementation.

Use established domain language and architectural decisions as project context.

Use `domain-modeling` when planning establishes or changes durable domain knowledge or architectural decisions.

Do not create artifacts merely to complete a sequence.

## Decision authority

Resolve technical choices autonomously when they remain within the agreed product contract and constraints.

Escalate to the user only when a decision requires an unresolved product, business, compatibility, cost, risk, or other value judgment.

When the user has delegated the decision, make the choice and preserve the material reasoning where appropriate.

## Review

When planning is complete, read [review.md](./review.md) and review the planning set.

Resolve material findings in the artifact that owns them and review again.

Planning completes only when the Proposal becomes:

`implementation-ready`

Do not begin implementation unless requested.

# plan/proposal.md

# Proposal

Every planned work item has one Proposal.

The Proposal is the canonical root of the work. It identifies the work, tracks its lifecycle, and references authoritative artifacts without duplicating them.

## Storage

Prefer the project's configured issue tracker when one exists.

Otherwise store the Proposal locally at:

    docs/proposals/<slug>.md

Reuse an existing Proposal when the work already has one.

Do not create both an issue and a local Proposal unless the project explicitly requires it.

## Contents

Keep the Proposal concise.

It should contain:

### Summary

Briefly describe the intended change and why it exists.

### Acceptance

Define the minimum observable conditions for considering the work successful.

Keep this concise when a PRD contains the detailed product contract.

### Artifacts

Reference authoritative artifacts that actually exist, such as:

- PRD
- RFC
- ADRs
- implementation tickets

Do not create placeholder artifacts merely to populate this section.

## Status

Use the Proposal to track the work through the engineering workflow.

For an issue tracker, use its configured workflow mechanism.

For a local Proposal, use frontmatter:

    ---
    status: planning
    ---

Valid states are:

- `planning`
- `implementation-ready`
- `implementing`
- `ready-for-verification`
- `verifying`
- `blocked`
- `done`

Do not introduce finer-grained states unless the project requires them.

## Updates

Update the Proposal when:

- workflow status changes
- an authoritative artifact is added, removed, replaced, or superseded
- implementation tickets are introduced

Do not copy detailed requirements, design reasoning, review findings, or implementation progress into the Proposal when another artifact owns that information.

## Local format

    ---
    status: planning
    ---

    # <Title>

    ## Summary

    <What is changing and why.>

    ## Acceptance

    - <Observable success condition>
    - <Observable success condition>

    ## Artifacts

    - PRD: <path>
    - RFC: <path>
    - ADR: <path>
    - Tickets: <path or tracker reference>

Omit artifact entries that do not exist.

# plan/prd.md

# PRD

Use a PRD only when the Proposal does not sufficiently define the product contract.

The PRD defines what the system should do, not how it should be implemented.

Use it to clarify material:

- behavior
- scope
- non-goals
- requirements
- acceptance criteria

Keep it proportional to the work.

Do not include technical design, implementation structure, or engineering choices. Those belong in the RFC or implementation.

Material product ambiguity must be resolved before the plan can become `implementation-ready`.

The user is the authority for unresolved product behavior and value judgments unless they explicitly delegate that authority.

# plan/rfc.md

# RFC

Use an RFC when meaningful technical decisions must be resolved before implementation.

Turn the established product contract into a sufficiently resolved technical design.

Focus only on decisions that materially constrain implementation, such as:

- system boundaries and responsibilities
- interfaces, protocols, schemas, or persistence
- lifecycle and failure behavior
- compatibility or migration
- material security, reliability, performance, or resource constraints
- meaningful verification seams

Do not prescribe routine implementation details that can safely be decided while coding.

## Decision authority

Resolve technical choices directly when they remain within the agreed product contract and constraints.

Do not ask the user to choose between technical alternatives merely because multiple viable approaches exist.

Escalate a decision only when the existing contract does not resolve a material:

- product behavior
- business preference
- compatibility commitment
- cost constraint
- risk tolerance
- scope trade-off
- other value judgment

When the user has explicitly delegated such a decision, choose the approach and record the material reasoning.

Document alternatives only when they materially explain the chosen design.

## Durable decisions

Use `domain-modeling` when a decision establishes durable domain language or an architectural constraint whose reasoning should outlive the RFC.

The RFC should retain the feature-specific design.

Do not duplicate the full RFC in an ADR.

## Completion

The RFC is complete when implementation can proceed without rediscovering a material technical decision.

Routine implementation details should remain open.

# plan/review.md

# Plan Review

Review the Proposal and its relevant planning artifacts as one implementation contract.

The purpose is to decide whether the work is `implementation-ready`.

## Readiness

The plan is ready when:

- intended behavior, scope, and acceptance are sufficiently defined
- material product and technical decisions are resolved
- Proposal, PRD, RFC, and relevant domain or architectural decisions are consistent
- important interfaces, compatibility, migration, or operational constraints are defined when relevant
- important verification expectations are clear
- implementation can proceed without inventing product behavior or architecture

Routine implementation details may remain open.

## Result

If ready, transition the Proposal to:

`implementation-ready`

If not ready, keep it in:

`planning`

Resolve findings in the artifact that owns them, then review again.

Do not compensate for missing planning decisions during implementation.
